# EasyPay

Заказ и оплата в ресторане по QR: блюдо сразу привязывается к человеку,
а не делится постфактум из общего счёта.

Надстройка над кассой (iiko / R-keeper). Сейчас — живое демо без кассы и
эквайринга; правила денег, зала и кухни уже те, с которыми пойдёт продукт.

**Демо:** [http://77.221.141.238](http://77.221.141.238)

Откройте ссылку на телефоне или выберите стол на экране. Персонал — `#/hall`
и PIN из таблицы ниже. Одинаковый `?t=` в двух вкладках = один стол, несколько гостей.

---

## Зачем это

Существующие QR-системы (нетмонет, SberFood, Sunday) делят **уже собранный**
счёт: поровну, по сумме или «отметь свои блюда». EasyPay сохраняет каждое
блюдо за персоной **в момент заказа**.

Это даёт:

- личный счёт без спора «кто что брал»;
- оплату своего или за весь стол;
- общие блюда с фиксированной долей — подсевший позже не платит за съеденное до него;
- аллергии как часть личности гостя, а не сноска в комментарии;
- залу — живую картину столов, кухне — очередь с цехами и раздачей.

MVP-канал — **PWA по QR**, без установки. Планшет официанта — фаза 2,
нативное приложение — фаза 3.

## Что умеет демо

### Гость (телефон по QR)

1. Сканирует QR стола → меню без барьера (имя спрашивается при первом блюде).
2. Выбирает имя, зверя-аватар и аллергии.
3. Кладёт блюда себе или «на стол», с модификаторами и комментарием.
4. Отправляет на кухню своё или весь черновик стола.
5. Видит статус: в очереди → готовится → несут → подано.
6. Может отменить своё, пока кухня не взялась.
7. Платит своё или за стол: СБП (приоритет), карта / T-Pay / SberPay / Mir Pay,
   либо просит официанта принять наличные.
8. Оставляет чаевые официанту **мимо счёта ресторана**.
9. Зовут официанта с причиной: помощь, счёт, вода — плюс свободный текст.

Имя и секрет гостя живут в `localStorage` ключом `easypay-identity-{стол}`.
Логина нет. Сосед по столу видит имена, но заказать или заплатить за вас
не может: каждое действие требует личного `x-guest-token`.

### Зал и экран стола

- План зала по зонам: терраса, основной зал, бар.
- Статусы стола считаются на клиенте каждую секунду без лишних запросов:
  свободен → гости сели → на кухне → ждёт оплаты → частичная оплата →
  оплачен → убрать.
- Алерты: сели и не заказали (7 мин), кухня задерживает (20 мин),
  ждёт оплаты (10 мин после подачи), зовёт официанта, платит наличными.
- Закрепление столов за официантом: чужой стол трогать нельзя
  (кроме «иду» на вызов).
- Наличные — два шага: гость создаёт просьбу, официант подтверждает,
  что физически взял деньги.
- Стол становится свободным по факту уборки (`clean`), не по таймеру.
- Менеджер видит журнал смены и реестр чеков со сверкой кассы.

### Кухня

Путь позиции жёсткий:

```
черновик → send → очередь → start (взяли) → ready (на раздаче) → serve (унёс гостю)
```

`ready` необязателен: если его пропустить, время готовности проставится
моментом подачи. Подать, не взяв в работу, нельзя. Повторная подача запрещена.

- Кухня и бар — разные цеха и разные пороги срочности
  (кухня 10/20 мин, бар 3/6 мин).
- Позиции одной волны одного стола группируются: тар-тар не уезжает без лазаньи.
- Аллергии гостя и комментарий доезжают до тикета; модификатор, который
  снимает аллерген, подписывается явно («Без сметаны — снимает лактозу»).
- Force-закрытие стола снимает висящее с плиты; повар подтверждает
  отмену кнопкой «Снял с плиты».

### Роли

Один список прав на сервере и в UI (`packages/domain/src/roles.ts`):

| Роль | PIN демо | Что видит |
|---|---|---|
| Официант Максим | `1111` | терраса (столы 12–15), зал, кухня, свой стол |
| Официант Оля | `2222` | основной зал (1–6) |
| Официант Рома | `3333` | бар (21, 22) |
| Повар Артём | `4444` | только кухня |
| Менеджер Ирина | `9999` | всё + журнал + реестр чеков + сброс стола |
| Владелец | `7777` | то же, что менеджер |

Сессия персонала — 12 часов, до 5 устройств на человека. Подбор PIN
режется по устройству (6 попыток / 5 мин), не по IP заведения.

## Денежная модель

Считает **только сервер**. Клиент показывает `totals` из снапшота и
никогда не называет сумму списания. Три правила, которые нельзя нарушать:

1. **Счёт — это отправленное на кухню.** Черновик корзины в долг не входит
   (`draftTotal` отдельно).
2. **Доля общего блюда фиксируется в момент отправки** (`line.sharedWith`).
   Подсевший позже за него не платит.
3. **Цена фиксируется в позиции** (`line.price`). Правка меню не
   переписывает открытые счета.

И ещё два, которые легко сломать обратно:

4. **Личный остаток ограничен остатком стола.** Если сосед уже закрыл
   стол целиком (`scope: full`), лично списывать нечего.
5. **Хвост округления забирает последний плательщик**, а доли на витрине
   складываются обратно в счёт. Иначе 490 ₽ на троих превращаются в 489,99
   и стол нельзя закрыть без `force`.

`join`, `lines`, `pay` и `tip` идемпотентны по `idemKey`: повтор после
обрыва не создаёт вторую персону, второе блюдо или второй платёж.

Закрытие стола отвечает 409 `unpaid` при остатке и 409 `kitchen pending`,
если на кухне ещё готовится еда этого стола. Оба снимаются только
`force: true` и пишутся в журнал.

## Репозиторий

Монорепо на npm workspaces. Границы жёсткие: `domain` не знает про HTTP
и хранилище, `api` не считает деньги сам, клиент не считает ничего, что
влияет на списание.

```
apps/api          HTTP + SSE: столы, смена, кухня, зал
apps/web          React 18, hash-роутинг: гость, зал, кухня, официант, QR-тенты
packages/domain   чистые правила: money, hall, kitchen, roles, allergens
packages/db       Postgres: схема, миграции, сиды из config
packages/config   меню, план зала, демо-персонал
docs/             PRD, архитектура, отчёты тестовых смен
infra/            docker-compose (Postgres 16 + Redis)
```

Сервер — источник истины по столу. Состояние за интерфейсом `store`:
память (тесты и запуск без базы) или Postgres (`EASYPAY_STORE=postgres`).
Мутация идёт через `store.withTable(id, apply)` — в Postgres это
`SELECT … FOR UPDATE` внутри транзакции, две одновременные оплаты не
спишут больше остатка.

Синхронизация — **SSE**, не WebSocket. Клиент подписывается на поток,
любая мутация рассылает **полный снапшот**. Оптимистичных правок UI нет:
POST → сервер → снапшот → экран.

```
QR на столе ──▶ гостевой PWA (React)
                    │  HTTP + SSE
                    ▼
              apps/api  ── store: memory | postgres
                    │
                    ├── domain/money     суммы, доли, округление
                    ├── domain/hall      статусы и алерты зала
                    ├── domain/kitchen   очередь и срочность
                    └── domain/roles     права персонала
```

## Запуск

Нужен **Node 22** (тесты и `dev:api` исполняют TypeScript напрямую).

```bash
npm install
```

Два процесса: Vite на `:5173` проксирует `/api` на `:8787`.

```bash
npm run dev:api   # сервер, PORT по умолчанию 8787
npm run dev       # клиент
```

Прод-сборка одним процессом (сервер сам отдаёт `apps/web/dist` со SPA-фолбэком):

```bash
npm run serve
```

### С Postgres

```bash
npm run db:up        # docker compose: Postgres 16 на :5433, Redis на :6380
npm run db:migrate
npm run db:seed
EASYPAY_STORE=postgres npm run dev:api
```

`DATABASE_URL` по умолчанию `postgres://easypay:easypay@127.0.0.1:5433/easypay`.
Полный сброс тома: `npm run db:reset`.

### Тесты

`node:test`, без внешних раннеров. Перед прогоном собирается domain.

```bash
npm test
npm test -w @easypay/domain
node --test packages/domain/tests/money.test.ts
```

## Экраны

Hash-роутинг, отдельного роутера нет. Стол берётся **только** из `?t=`,
дефолта нет: без параметра — выбор стола, неизвестный стол — понятная ошибка.

| Адрес | Кто | Что |
|---|---|---|
| `/?t=12` | гость | меню → корзина → кухня → оплата |
| `/` | гость | выбор стола из плана зала |
| `/#/hall` | персонал | план зала, сводка смены, журнал, чеки |
| `/?t=12#/waiter` | официант / менеджер | один стол: гости, лента, оплаты, наличные |
| `/#/kitchen` | повар / зал | очередь, раздача, отмены |
| `/?t=12#/qr` | печать | QR-тент одного стола |
| `/#/qr` | печать | лист тентов на все столы |

Сервисный вход менеджера: `/?mtoken=<токен>#/hall` — токен печатается
в логе при старте, если `EASYPAY_MANAGER_TOKEN` не задан.

Гостевой поток по `ui.screen`:

`welcome → menu → cart → status → payment → tips → done`

Модалки — `ui.sheet`: карточка блюда, имя, отправка, вызов официанта.

## API

База: `/api/t/:tableId/…`. POST, если не сказано иначе. Гостевые ручки
требуют `x-guest-token` и открытый стол; персонал — `x-staff-token`
и право роли. EventSource не умеет заголовки, поэтому в SSE токен
в query (`?g=` гость, `?token=` сотрудник).

### Стол

| Метод | Путь | Кто | Действие |
|---|---|---|---|
| GET | `/api/t/:id` | свой / персонал с правом `table` | полный снапшот; постороннему — заглушка; повару стол не показывают |
| GET | `/api/t/:id/stream` | то же | SSE, полный снапшот на каждую мутацию |
| POST | `…/join` | гость | сесть: имя, зверь, аллергии. Первое действие на закрытом столе открывает новую сессию |
| POST | `…/lines` | гость | блюдо в корзину; 409, пока аллерген не подтверждён |
| POST | `…/remove` | гость | убрать неотправленное |
| POST | `…/send` | гость | на кухню: своё или весь стол |
| POST | `…/cancelMine` | гость | отмена, пока кухня не взялась |
| POST | `…/pay` | гость | списание по `scope` (`own` / `equal` / `full`); сумму считает сервер |
| POST | `…/cashIntent` | гость | «примите наличные» |
| POST | `…/cancelCash` | гость | передумал, платит телефоном |
| POST | `…/tip` | гость | чаевые официанту, не в счёт; можно в течение 30 мин после закрытия |
| POST | `…/call` | гость | вызов: `help` / `bill` / `water` + текст |

### Персонал по столу

| Метод | Путь | Право | Действие |
|---|---|---|---|
| POST | `…/start` | cook+ | взял в работу |
| POST | `…/ready` | cook+ | готово, на раздаче |
| POST | `…/serve` | cook+ / зал | унёс гостю |
| POST | `…/dismiss` | cook+ | снял отмену с плиты |
| POST | `…/ack` | waiter+ | «иду» — на любом столе |
| POST | `…/cash` | waiter+ | подтвердил наличные |
| POST | `…/close` | waiter+ | закрыть стол; `force` пишет в журнал |
| POST | `…/clean` | waiter+ | стол убран |
| POST | `…/reset` | manager | принудительно освободить |

`start` / `ready` / `serve` обязаны нести `sessionId` стола.

### Смена и справочники

| Метод | Путь | Кто |
|---|---|---|
| POST | `/api/staff/login` | PIN |
| GET | `/api/staff/me` | сессия |
| POST | `/api/staff/logout` | сессия |
| GET | `/api/staff/roster` | менеджер |
| GET | `/api/log` | менеджер, журнал |
| GET | `/api/shift/checks` | менеджер, реестр чеков и сверка |
| GET | `/api/menu` | все |
| GET | `/api/hall` + `/stream` | право `hall` |
| GET | `/api/kitchen` + `/stream` | право `kitchen` |

Постороннему `GET /api/t/:id` отдаёт только стол, статус и число посадок —
не имена, не аллергии, не счета. Соответствие «ручка сервера → место
на экране» ведётся в [`docs/architecture/api-ui-matrix.md`](docs/architecture/api-ui-matrix.md).

|---|---|

| `EASYPAY_MANAGER_TOKEN` | сервисный вход с правами менеджера |

| `EASYPAY_ANY_TABLE` | `1` — тесты могут открыть стол вне плана зала |

## Что в демо ещё не продукт

Это рабочий прототип ресторанной смены, не готовый SaaS.

- Нет HTTPS, домена и настоящего эквайринга: `pay` дописывает платёж
  в состояние стола. QR СБП на экране — макет.
- Фискальный чек по 54-ФЗ не бьётся. Гость получает чек заказа с номером
  и составом, не документ ОФД.
- Кассы нет: нет `PosAdapter`, стоп-листа из iiko/R-keeper, сервис-печати.
- Меню и персонал — файлы в репозитории, не кабинет заведения.
- Нет состояния «ошибка платежа и повтор», нет возвратов.
- Мастер-токен менеджера остаётся служебным входом мимо ролей.
- `scope: equal` («поровну») есть в API, на экране гостя выбора нет —
  при разных заказах это почти всегда не то, чего хочет человек.

План перехода (мультиарендность, кабинет, касса, эквайринг, несколько
инстансов): [`docs/architecture/production.md`](docs/architecture/production.md).
