# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

EasyPay — заказ и оплата в ресторане по QR с привязкой блюд к персоне **в момент заказа**
(а не постфактумное деление счёта). Надстройка над кассой (iiko / R-keeper), Россия.

Репозиторий — монорепо на npm workspaces:

```
apps/api        — HTTP + SSE сервер на TypeScript: столы, смена, кухня, зал
apps/web        — клиент: гостевой поток по QR (screens/, sheets/) и экраны
                  персонала — кабинет 4.0 (cabinet/, вход по PIN — staff/)
packages/domain — правила без ввода-вывода (TS): money, hall, kitchen, roles, allergens
packages/db     — Postgres: схема, миграции, наполнение из packages/config
packages/config — начальные данные заведения: menu.json, hall.json, staff.json
                  (дальше меню, персонал и настройки правятся из кабинета и живут в БД)
docs/           — продуктовая часть: PRD, архитектура, план перехода на БД
infra/          — окружение (docker-compose появится на этапе БД)
```

Граница жёсткая: `domain` не знает про HTTP и хранилище, `api` не считает деньги сам,
клиент не считает ничего, что влияет на списание. План перехода в продукт (БД, кабинет,
модули) — `docs/architecture/production.md`.

## Команды

Всё запускается из корня репозитория.

```bash
npm install
```

Разработка требует **двух** процессов — Vite проксирует `/api` на `localhost:8787`:

```bash
npm run dev:api   # сервер (PORT по умолчанию 8787)
npm run dev       # клиент на :5173 с проксированием /api
```

Прод-сборка и запуск одним процессом (сервер сам отдаёт `dist` со SPA-фолбэком):

```bash
npm run serve
```

Тесты — `node:test`, без зависимостей:

```bash
npm test
```

Один пакет или один тест: `npm test -w @easypay/domain`,
`node --test packages/domain/tests/money.test.js`.

Линтера нет. **Сервер и домен на TypeScript**: Node 22 исполняет `.ts` напрямую (тесты
гоняются без сборки), для VPS с Node 18 собираем в JS через `npm run build`.

Маршруты (hash-роутинг, роутера нет, разбор — `apps/web/src/cabinet/route.ts`): `/` — гость,
`/#/admin/<раздел>` — кабинет менеджера (`overview`, `shifts[/<id>]`, `checks[/<смена>]`, `debts`,
`menu`, `staff`, `log`, `settings`, `close`), `/#/hall[/<стол>]` — зал и стол, `/#/kitchen` и
`/#/bar` — очереди цехов, `/#/qr` — QR-тент стола (без `?t=` — лист тентов на все столы).
Старый `?t=6#/waiter` ведёт на `#/hall/6`.

**Стол берётся только из `?t=…`, дефолта нет** (раньше молча подставлялся стол 12): без
параметра гость видит экран выбора стола `apps/web/src/screens/TablePicker.tsx`, неизвестный стол —
понятную ошибку. Стол считается известным, если он есть в `packages/config/hall.json`. Одинаковый `t`
в двух вкладках = мультиплеер за одним столом.

Экраны персонала закрыты **входом в смену по PIN**. Сотрудники живут в БД и правятся в
кабинете («Персонал»: PIN придумывает сервер и показывает один раз, хранится хеш; увольнение
гасит сессии сразу); `packages/config/staff.json` — только начальное наполнение, его PIN-коды
перекрываются переменной `EASYPAY_STAFF_PINS="max=4821,boss=7390"`. Роли и права —
в `packages/domain/roles.js`, один список для сервера и клиента: повар видит только кухню, официант —
зал/стол/кухню и свои закреплённые столы, менеджер — всё плюс журнал смены. Сессия живёт
12 часов, попытки подбора PIN ограничены.

Токен в адресе (`?token=`) принимается только для чтения потоков `*/stream`; права на поток
перепроверяются на каждой рассылке. Гостевые действия снаружи (через прокси) ограничены по
частоте (`apps/api/src/rateLimit.ts`), адрес клиента берётся из `X-Forwarded-For`, который
выставляет Caddy. Сид (`packages/db`) PIN уже заведённых сотрудников не перезаписывает.

Мастер-токен `EASYPAY_MANAGER_TOKEN` (в логе при старте, если переменной нет) остался
сервисным входом с правами менеджера: ссылка `/?mtoken=<токен>#/hall` кладёт его в
localStorage. Им же удобно проверять деплой curl-ом.

```bash

```

смены не выкидывает.

публиковал устаревшую мок-версию.

## Архитектура

**Сервер — источник истины по состоянию стола.** `apps/api/src/index.ts` держит правила,
а состояние живёт в хранилище за интерфейсом (`apps/api/src/store/`): `memory` для тестов
и запуска без базы, `postgres` для продукта. Переключается `EASYPAY_STORE=postgres`
плюс `DATABASE_URL`. Мутация идёт через `store.withTable(id, apply)` — в Postgres это
`SELECT … FOR UPDATE` внутри транзакции, поэтому две одновременные оплаты не спишут
больше остатка. На живом стенде поднят Postgres 16: рестарт больше ничего не теряет.
Сессия стола: `{sessionId, status: 'open'|'closed', personas[], lines[], payments[], seq}`.

**Синхронизация — SSE**, не WebSocket. Клиент подписывается на `GET /api/t/:table/stream`,
любая мутация вызывает `broadcast(tableId)`, который рассылает **полный снапшот** стола.
Клиент никогда не мутирует состояние локально «оптимистично»: POST → сервер → снапшот → UI.

API (всё под `/api/t/:tableId/…`, POST если не сказано иначе):
`GET ''` — снапшот, `GET stream` — SSE, `join`, `lines`, `remove`, `send`, `pay`, `tip`,
`call` (гостевые, требуют заголовок `x-guest-token` и открытого стола), `start`, `serve`, `ack`,
`close`, `reset` (персонал: заголовок `x-staff-token`, право по роли), плюс
`POST /api/staff/login`, `GET /api/staff/me`, `POST /api/staff/logout`, `GET /api/log`,
`GET /api/hall`, `GET /api/kitchen` и их `/stream`-версии.

Чаевые (`tip`) — отдельная сущность, **в счёт стола не входят**: официант видит их
на своём экране. `call`/`ack` — вызовы официанта копятся очередью (`calls[]`), снимаются по `callId`; у гостя
один открытый вызов, повторы копятся в нём (`repeats`), `ack` принимает `reply` — ответ гостю.
Отправка на кухню (`send`) заново проверяет стоп-лист и аллергены: корзина могла пролежать.
Путь позиции на кухне строгий: `send` → `start` → `serve`; подать, не взяв в работу,
нельзя, повторная подача запрещена, а действие обязано нести `sessionId` стола.
Путь позиции длиннее, чем кажется: `send` → `start` (повар взял) → `ready` (готово,
стоит на раздаче) → `serve` (официант унёс гостю). «Готово» и «подано» — разные события
разных людей; `ready` необязателен, но если его пропустить, время готовности проставится
моментом подачи. Гость может отменить своё через `cancelMine`, пока кухня не взялась.

`close` отвечает 409 `unpaid` при неоплаченном остатке и 409 `kitchen pending`, если на
кухне ещё готовится еда этого стола — оба снимаются только `force: true`, это пишется в
журнал; всё висящее на кухне при этом отменяется и повар видит отмену, пока не подтвердит
её через `dismiss`. Закрытие уже закрытого стола отвечает 409 `already closed`.
Стол становится свободным по факту уборки (`clean`), а не по таймеру. Модификаторы блюд (`options`: острота, прожарка, лёд) описаны в
`packages/config/menu.json`, сервер принимает только значения из меню и подставляет дефолт.

`join`, `lines` и `pay` **идемпотентны по `idemKey`** из тела: сервер держит ответ в
`idempotency` Map и на повтор отдаёт тот же результат, не выполняя действие второй раз.
Ключ платежа живёт на клиенте до успешной оплаты (`apps/web/src/screens/Payment.tsx`), поэтому
ретрай после обрыва не создаёт второй платёж.

**Денежная модель — одна на всех**: `packages/domain/money.js` (`computeTotals`, `amountFor`,
`round2`) импортируется и сервером, и `apps/web/src/store.tsx`; типы — в `packages/domain/money.d.ts`.
Три правила, которые нельзя нарушать:

1. **Счёт — это отправленное на кухню.** Черновик корзины (`sent: false`) в `tableTotal`
   не входит и долгом стола не считается; он виден отдельно как `draftTotal`.
2. **Доля общего блюда фиксируется в момент отправки**: `line.sharedWith` — список персон
   на этот момент. Подсевший позже за него не платит, заплативший раньше не переплачивает.
3. **Цена фиксируется в позиции** (`line.price`) — правка меню не переписывает открытые счета.

Сумму списания считает **только сервер**: `pay` вызывает `amountFor` сам и клампит её
неоплаченным остатком, а снапшот отдаёт готовые `totals` (по столу и по каждой персоне) —
гость видит ровно те числа, которые спишутся. `scope` обязателен: запрос без него
отвечает 400, иначе неполный запрос молча списывал весь счёт.

Два правила, которые легко нарушить обратно:

4. **Личный остаток ограничен остатком стола.** За гостя мог заплатить сосед (`scope: full`),
   и тогда лично он не должен ничего. Показанное число и есть списываемое — попытка
   «красиво» распределить чужую переплату пропорционально давала микроплатежи на 60 копеек.
5. **Хвост округления забирает последний плательщик** (`absorbRounding`), а доли на витрине
   складываются обратно в счёт (`splitRounded`): иначе 490 на троих превращается в 489,99,
   и полностью рассчитавшийся стол нельзя закрыть без `force`.
6. **«Поровну» — равная доля всего счёта минус уже внесённое гостем** (`equalDueOf`), не
   больше остатка стола. Кто-то заплатил «поровну» — дальше только поровну или весь стол:
   это держит **сервер** (`pay`, `cashIntent`, `cash` → 409 `equal split in progress`), а не
   только экран — смесь давала копеечные хвосты. Прежние правила ломались вживую: «треть
   счёта» недоплачивала после чужого «своего», «остаток на неплативших» после дозаказа делил
   на одного и показывал весь стол (живой стол 3).

**Наличные — два шага.** Гость не может заплатить наличными с телефона: `cashIntent`
создаёт просьбу (денег в счёте нет), официант физически берёт деньги и подтверждает
действием `cash`. Сумму клампит сервер, в платеже сохраняется, кто взял.

**Аллергии — часть личности гостя.** `join` принимает `allergies` (только значения из
справочника, чужое слово — 400 с подсказкой), заказ блюда с заявленным аллергеном
отвечает 409, пока гость не подтвердит `confirmAllergen: true`. Кухня видит и комментарий
гостя, и то, какой модификатор снимает аллерген: «Без сметаны — снимает лактозу».

**Приватность стола.** `GET /api/t/:id` и его SSE отдают полный снапшот только своим:
гостю этого стола (по `x-guest-token`, в потоке — `?g=`) или сотруднику с правом `table`
(в потоке — `?token=`). Постороннему уходит заглушка: стол, статус, число мест и посадок.
Повару стол не показывают вовсе — его рабочее место кухня, а не счета гостей.

**Идентичность гостя** — `localStorage` по ключу `easypay-identity-${tableId}`, хранит
`{sessionId, personaId, guestToken}`. `join` выдаёт личный секрет гостя; все гостевые
действия требуют заголовок `x-guest-token` — иначе сосед по столу мог бы заказать за вас
(personaId виден всем в снапшоте). Логина нет. При закрытии/сбросе стола сервер выдаёт новый
`sessionId`, клиент видит расхождение и забывает личность — иначе гость упирался бы в
мёртвый стол (см. коммит `17e82f6`). Первое действие на закрытом столе (`join`) открывает
новую сессию с чистого листа.

**Клиент** — React 18 без роутера и без стейт-менеджера: один контекст `apps/web/src/store.tsx`
(`StoreProvider` / `useStore`) держит серверный снапшот (`snap`), чисто клиентский
`UiState` (`screen`, `sheet`, шаги оплаты, чаевые, тост) и все server-actions, обёрнутые
в `guard()` с тостом об ошибке. Экран гостя — переключение по `ui.screen`
(`welcome → menu → cart → status → payment → tips → done`), модалки — `ui.sheet`
(`dish` / `name` / `send`); отдельного экрана «выбор персоны» нет: имя и зверь
спрашиваются инлайн при первом добавлении блюда.

`useAutoNav()` в `apps/web/src/App.tsx` реагирует на действия **других** гостей (кто-то оплатил весь
стол / отправил всё на кухню), чтобы никто не завис на потерявшем смысл экране. Это частая
причина «странных» переходов при отладке.

**Кабинет 4.0** — `apps/web/src/cabinet/`: светлая тема `c-*` (`cab.css`), каркас `Shell.tsx`
(рабочие места «Кабинет · Зал · Кухня · Бар» по правам роли, боковое меню кабинета), зал
`HallPage.tsx`, стол `TableView.tsx`, кухня и бар `KitchenPage.tsx`, разделы менеджера в
`cabinet/admin/` (обзор с X-отчётом, мастер закрытия смены, долги и решения, смены с Z-отчётами,
реестр чеков, журнал, конструктор меню `admin/menu/`, персонал, настройки). Менеджер после входа
попадает в `#/admin/overview`.

План зала — `packages/config/hall.json` (зоны, столы, посадка); его читает и сервер. Данные зала —
`GET /api/hall` и SSE `/api/hall/stream?token=…` (EventSource не умеет заголовки — токен в query).
Сервер отдаёт компактные карточки, а статусы, таймеры и алерты считает `packages/domain/hall.ts` —
одинаково на сервере и клиенте. Кухня — `GET /api/kitchen` и `/api/kitchen/stream`; правила очереди
и срочности — `packages/domain/kitchen.ts`.

**Смена — событие.** Менеджер открывает смену (`POST /api/shift/open`) и закрывает мастером
(`POST /api/shift/close`: долги решены, касса пересчитана, расхождение с комментарием) — Z-отчёт
замораживается в `shifts.report`. Без открытой смены новые столы не открываются (`join` → 409
`shift closed`); открытые при закрытии столы переносятся в следующую. Отчёт считает
`packages/domain/shift.ts` (часы — по поясу заведения). Долги решаются в `/api/decisions/*`:
«взыскано» (наличными/переводом/СБП) или «списано на заведение»; удержание с официанта не делаем
до юриста (ТК РФ ст. 137, 138, 241).

**Меню, персонал, настройки — в БД, правятся из кабинета.** Меню: черновик и публикация
(`/api/menu/editor|draft|publish|discard`), фото блюд — в `menu_photos` (`/api/menu/photo/<id>`),
гость берёт меню с `/api/menu/live` до первого кадра и перечитывает, когда в снимке меняется
`menuVersion`. Снятое блюдо заказать нельзя, но в открытом счёте оно называется по имени.
Настройки заведения — одна схема `packages/domain/settings.ts` (`venues.settings`), читают все
(`GET /api/settings`), меняет менеджер; снимки несут `settingsVersion`. Каждая настройка
что-то делает: выключенный способ оплаты, делёж или чаевые сервер не примет (409), пороги
красят зал и кухню, правила смены решают, можно ли закрыть с долгом.

**Стили** — `apps/web/src/styles.css` с CSS-переменными `--ep-*` и переключателем темы через
`document.documentElement.dataset.theme` (инлайн-скрипт в `index.html`). Активна одна тема
`classic`; тема `seasons` была реализована и откачена (`3c3df70`) — архитектура переменных
осталась, новая тема подключается заменой блока переменных. Компоненты используют
инлайн-стили поверх этих переменных; общие примитивы — `apps/web/src/ui.tsx`, аватары-звери
(SVG, не эмодзи) — `apps/web/src/avatars.tsx`. Гость 4.x живёт на токенах `g-*`
(`apps/web/src/guest/g4.css`), кабинет — на `c-*` (`apps/web/src/cabinet/cab.css`); оба файла
подключены в `theme.css` после `tailwindcss` — иначе токены `@theme` не превратятся в классы.

## Продуктовые инварианты (нарушать только осознанно)

- **Аватары персон — иллюстрированные звери, не эмодзи и не буквы.**
- **Оплата по умолчанию в конце** (сидячий ресторан); предоплата — переключатель на будущее.
- **СБП — приоритетный способ оплаты**; чаевые — напрямую официанту, не через счёт.
- **Касса — источник истины** в продуктовой архитектуре; все мутации через `PosAdapter`
  с идемпотентными ключами (`docs/architecture/pos-integrations.md`). В демо кассы нет.
- **MVP-канал — только web-app (PWA) по QR**; планшет — фаза 2, нативка — фаза 3.
- Суммы всех опций оплаты обязаны считаться от **неоплаченного остатка** —
  антидвойная-оплата, см. `docs/architecture/payments-fiscal.md` и `docs/prototype/review.md`.

## Как мы работаем над продуктом

Проверка идёт сменами мультиагентов: у каждой роли свой характер и своя боль
(гость-скептик, аллергик, компания с делёжкой, повар, официант, управляющая, ломатель).
Порядок жёсткий и выстрадан на практике:

**находки копятся до конца смены → правим одной пачкой → pull request → и только потом

сервера и поверхностей интерфейса ведётся в `docs/architecture/api-ui-matrix.md`.

## Известные ограничения демо

HTTPS нет (нет домена — из-за этого `crypto.randomUUID()` в браузере недоступен, ключи
генерит `apps/web/src/keys.ts`), нет интеграции с кассой и реального эквайринга (`pay`
просто дописывает платёж), нет состояния «ошибка платежа», фискальный чек не пробивается —
гостю отдаётся чек заказа с номером и составом, а не документ по 54-ФЗ. Мастер-токен
менеджера остаётся сервисным входом мимо ролей. Список продуктовых дыр —
`docs/prototype/review.md`, `docs/prototype/shift-2-findings.md`, `shift-3-findings.md`
и `shift-4-findings.md`.
