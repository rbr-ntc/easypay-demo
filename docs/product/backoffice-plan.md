# Смена, чеки, кабинет и UX гостя — план

Документ собран по итогам ручного теста после редизайна 3.0. Факты про текущее
устройство взяты из кода, а не из памяти: где сказано «сейчас так», это можно
проверить по ссылке на файл.

Общий план перехода в продукт — `docs/architecture/production.md` (§6 «Кабинет»,
§11 «Этапы»). Этот документ его не заменяет, а раскладывает раздел «Кабинет» и
этап «Смена и деньги» на экраны и порядок работ.

---

## 1. Что сейчас сломано логически

**1.1. Смены как события нет.** В базе есть таблица `shifts` с полями `opened_at`,
`closed_at`, `closed_by`, `report` (`packages/db/migrations/0001_init.sql`), но ни одного
API, чтобы смену открыть или закрыть, и ни одной кнопки. На стенде одна смена — с
первого запуска. Следствия:

- реестр чеков копит всё с первого дня и показывает последние 100;
- «ваши чаевые» у официанта считаются **за всё время**, а не за смену: запрос
  `tipsByStaff` в `apps/api/src/store/postgres.ts` не фильтрует по смене;
- нет истории смен — нечего сравнивать, некому показать «вчера было так».

**1.2. Долг — тупик.** Закрыть стол с долгом можно (`close` с `force`). Дальше долг
живёт только числом в сверке. Нет списка должников, нет действия «взыскали» или
«списали», нет причины и ответственного. У переплаты путь есть — `refund`,
у долга — никакого. Отсюда «столы закрыты с долгом — куда идти за решением».

**1.3. Бухгалтерия внутри операционного экрана.** Правая колонка зала шириной 340 px
(`apps/web/src/hall/Hall.tsx`) держит сводку, реестр чеков и журнал. Реестр
раскрывается вниз лентой до 100 чеков, без поиска и фильтров
(`apps/web/src/hall/ShiftChecks.tsx`). Менеджер видит зал и бухгалтерию одной
портянкой.

**1.4. Настройки заведения зашиты в файлы.** Меню, персонал, PIN-коды, план зала —
`packages/config/*.json`. Правка цены или стоп-лист = разработчик + деплой. Стоп-лист
сейчас — флаг `"stop": true` в файле.

**1.5. У менеджера нет «дома».** Зал, кухня и экран стола — три отдельных адреса,
связанные ссылками в шапке. Куда идти за отчётом, за чеками, за решением — неочевидно.

## 2. Главный принцип: два режима, не смешивать

| | **Смена** (операционка) | **Кабинет** (бэк-офис) |
|---|---|---|
| Вопрос | Что происходит **сейчас** | Что **было** и как всё **настроено** |
| Кто | официант, повар, менеджер на ногах | менеджер, владелец за столом |
| Устройство | планшет, телефон | компьютер |
| Экраны | зал, кухня, стол, закрытие смены | обзор, смены, чеки, долги, меню, зал, персонал, журнал |
| Вход | PIN | логин и пароль (см. `production.md` §5) |
| Адрес | `/#/hall`, `/#/kitchen`, `/#/waiter` | `/#/admin/...` (в продукте — `/admin`) |

Сейчас кабинетные вещи (реестр, журнал) засунуты в операционный экран — отсюда каша.
Правило: **в операционке — только то, на что нужно отреагировать в ближайшие минуты**.
Всё остальное — в кабинете, со ссылкой-счётчиком из зала.

## 3. Жизненный цикл смены

**Открытие.** Менеджер нажимает «Открыть смену» (решение §9). В смене фиксируется:
кто открыл, когда, кто из персонала вышел, какие столы перенесены из прошлой.

**Во время.** Сводка в зале — это X-отчёт: промежуточные цифры без закрытия.

**Закрытие — мастер из трёх шагов**, а не одна кнопка:

1. **Что мешает закрыть.** Список блокеров, у каждого — действие прямо здесь:
   - открытые столы → закрыть / перенести в следующую смену (выбор менеджера, §9);
   - еда на кухне не отдана → подать / снять;
   - наличные «в пути» (гость попросил, официант не подтвердил) → подтвердить / отменить;
   - переплаты, которые надо вернуть → вернуть;
   - неснятые вызовы официанта.
2. **Разбор денег.** Каждый долг смены получает решение (§4). Каждое расхождение
   сверки — объяснение текстом. Закрыть с неразобранным расхождением нельзя, только
   с комментарием менеджера — он попадёт в отчёт.
3. **Итог.** Z-отчёт: выручка, по способам оплаты, чеков, гостей, средний чек,
   чаевые по официантам, долги и как решены, возвраты, списания с кухни. Менеджер
   подтверждает — отчёт замораживается в `shifts.report` и больше не меняется.

После закрытия зал пустеет от закрытых столов прошлой смены, счётчики обнуляются.

## 4. «Требует решения» — одна очередь вместо разбросанных проблем

Отвечает на вопрос «куда идти за решением». Всё, что требует действия менеджера,
попадает в одну очередь с счётчиком в шапке:

| Что | Действия |
|---|---|
| Стол закрыт с долгом | взыскано (наличными / переводом / СБП) · списано на заведение (причина) |
| Переплата не возвращена | вернуть (уже есть `refund`) |
| Расхождение сверки | объяснить · открыть чеки |
| Стол открыт дольше N часов | закрыть · это нормально (банкет) |
| Отмена после оплаты | вернуть · оставить |

Каждое решение — запись в журнал: кто, когда, сумма, причина.

**Что нужно на сервере:** сущность урегулирования долга — `settlements`
(`session_id`, `kind: collected | written_off`, `amount`, `method`, `reason`, `by`, `at`).
Долг смены тогда = долг чеков − урегулировано, и сверка учитывает решения.

## 5. Кабинет: разделы и экраны

Навигация — боковое меню слева на компьютере, сворачивается на планшете.
Порядок — по частоте использования.

**5.1. Обзор (дом).** Текущая смена в цифрах (X-отчёт), очередь «требует решения»,
кнопка «Закрыть смену», последние 3 смены одной строкой для сравнения.

**5.2. Смены.** Таблица: дата, часы, кто открыл и закрыл, выручка, чеков, гостей,
средний чек, чаевые, долг, статус сверки (✓ / ✕ с суммой). Строка → **карточка смены**:
метрики, выручка по часам, по официантам, топ и аутсайдеры блюд, чеки этой смены,
журнал этой смены, Z-отчёт (печать / PDF).

**5.3. Чеки.** Таблица с фильтрами вместо раскрывающейся ленты:
- период / смена, стол, официант;
- статус: оплачен полностью · долг · возврат · есть отмены · чаевые;
- поиск по номеру чека и названию блюда.

Клик по строке → панель справа: состав, кто что заказал, платежи, чаевые, таймлайн
стола (сели → заказали → подали → оплатили → закрыли).

**5.4. Долги и решения.** Очередь из §4 целиком, с историей решённого.

**5.5. Меню — конструктор.**
- категории: порядок перетаскиванием, скрыть;
- блюдо: название, описание, цена, порция, ккал, фото (загрузка + автор и лицензия —
  уже есть `photo-credits.json`), аллергены (**обязательное поле с явным «нет»**),
  модификаторы с влиянием на аллергены и цену, теги;
- стоп-лист тумблером — мгновенно у всех гостей;
- черновик → «опубликовать»; предпросмотр «как видит гость»;
- цена в открытых счетах не меняется — это уже гарантировано (`line.price`).

**5.6. Зал.** Зоны, столы, места, закрепление официантов, печать QR-тентов.

**5.7. Персонал.** Сотрудники, роли, сброс PIN, активные сессии и «завершить все».

**5.8. Журнал.** Фильтры по столу, сотруднику, периоду, типу события, сумме; экспорт.

**5.9. Настройки.** Пороги алертов зала и кухни (сейчас зашиты в `packages/domain/hall`
и `kitchen`), реквизиты, позже — касса и эквайринг.

## 6. Операционный экран: что убрать и что добавить

- **Зал:** убрать реестр чеков и журнал из правой колонки. Оставить план, «внимание»,
  короткую сводку. Добавить счётчик «требует решения» (ведёт в кабинет) и кнопку
  «Закрыть смену» у менеджера.
- **Официант:** только своё — мои столы, мои чаевые **за эту смену**.
- **Стоп-лист в один тап из кухни и зала,** не только из кабинета: повар первым
  узнаёт, что закончилось.
- **Единая шапка навигации:** Зал · Кухня · Кабинет (менеджеру) · смена и кто на ней.
- **Экраны персонала на планшете** под адаптацию не проверялись — проверить вместе
  с редизайном.

## 7. Гостевой UX на телефоне — наблюдения для редизайна

Это наблюдения и гипотезы, а не приговор: проверять на живых гостях.

1. **Меню слишком «высокое».** Каждое блюдо с фото — карточка 280 px; на экран 915 px
   помещается два с половиной блюда, всё меню — около 10 000 px ленты. Меню читают
   глазами, быстро. Гипотеза: 1–2 крупные карточки «рекомендуем» на категорию,
   остальное — строки с миниатюрой, как у Wolt и Яндекс Еды.
2. **Шапка занимает ~200 px** (22 % экрана): значок, стол, «Официант», поиск, категории.
   При прокрутке не сжимается. Гипотеза: сворачивать до строки категорий, поиск —
   иконкой.
3. **Стекло закрывает ~40 % фото.** Фото — главное, что продаёт блюдо.
4. **Всё жирное.** Названия, цены, подписи — extrabold. Нет иерархии, глазу не за
   что зацепиться. Гипотеза: два веса на весь интерфейс.
5. **Две системы карточек рядом.** Фото на стекле и тёмная строка с полосатой
   заглушкой «фото готовится» — выглядит, будто часть меню сломана.
6. **Много тёмно-зелёного на кремовом.** Тяжёлые блоки; для еды, вероятно, нужно светлее.
7. **Нет настроения и нет «героя».** Меню начинается с поиска — ни фото заведения, ни
   рекомендаций, ни приветствия.
8. **Экран «Стол»:** много пустоты, служебное («Я другой гость») на видном месте.
9. **Мелочи, из которых складывается «сексуально»:** нет анимации «блюдо улетело
   в стол», нет плавной подгрузки фото, нет тактильного отклика на добавление.

## 8. Порядок работ

Оценки грубые, для порядка величины.

**Этап A — логика и данные, дизайн не нужен, можно начинать сразу.**
- A1. Жизненный цикл смены: открытие / закрытие через API, блокеры, заморозка
  отчёта, чаевые и сводка строго по смене. Тесты. *~2–3 дня.*
- A2. Урегулирование долгов (`settlements`) и API очереди «требует решения». *~2 дня.*
- A3. Меню, персонал и зал — из JSON в базу, API правки, стоп-лист через API. *~3–4 дня.*

**Этап B — кабинет, после макетов из Claude Design.**
- B1. Каркас кабинета: навигация, вход, «Обзор». 
- B2. Смены, чеки, мастер закрытия смены.
- B3. Конструктор меню.
- B4. Зал, персонал, журнал.
- B5. Очистка операционного зала: убрать реестр и журнал, добавить счётчик и навигацию.

**Этап C — гостевой редизайн** по новым макетам с учётом §7.

Процесс прежний: находки копятся, правим пачкой, PR, потом стенд.

## 9. Решения

**Приняты (2026-09-23):**

1. **Открытые столы при закрытии смены — выбор человека, не правило.** В мастере
   закрытия у каждого открытого стола две кнопки: «закрыть сейчас» и «перенести
   в следующую смену». Перенесённый стол живёт в новой смене, его выручка
   считается там, а в Z-отчёте старой смены он виден строкой «перенесено».
2. **Смену открывает менеджер** — явной кнопкой. Без открытой смены гостевой
   заказ не принимается, в зале баннер «смена не открыта».
3. **Долг: «взыскано» — точно.** Способы: наличными, переводом, СБП, с записью кто
   и когда.

**Открытые вопросы:**

4. **Что ещё можно сделать с долгом.** «Списано на заведение» — вероятно, нужно:
   иначе долг, который никто не вернёт, висит вечно. **Удержание с официанта — не
   закладываем до консультации с юристом:** удержания из зарплаты в РФ ограничены
   Трудовым кодексом (ст. 137, 138, 241 — материальная ответственность и её пределы).
   Нужен ответ юриста: допустимо ли это вообще и в каком оформлении.
5. **Кабинет на том же адресе** (`/#/admin` в демо, `/admin` в продукте) — предлагаю так.
6. **Цены в демо — из кабинета.** В продукте источник цен — касса (`production.md` §8);
   для демо это не мешает.

## 10. Бриф для Claude Design

Что нарисовать, по приоритету. Палитра и компоненты — из «Ель и лайм»
(`docs/design/easypay-3.0-handoff.md`), но для кабинета, вероятно, нужна светлая
«рабочая» версия: он живёт на мониторе по несколько часов.

**Кабинет (компьютер, 1440):**
1. Каркас: боковое меню, шапка со сменой и счётчиком «требует решения».
2. Обзор: X-отчёт, очередь решений, «Закрыть смену».
3. Мастер закрытия смены — 3 шага; состояния «всё чисто», «есть блокеры»,
   «есть расхождение».
4. Список смен → карточка смены с графиком по часам и Z-отчётом.
5. Чеки: таблица с фильтрами + панель чека справа; пустое состояние, фильтр
   «только с долгом».
6. Долги и решения: карточка долга с действиями «взыскано» / «списано».
7. Конструктор меню: список категорий и блюд, форма блюда, стоп-лист, предпросмотр.
8. Зал, персонал, журнал — можно проще, таблицами.

**Смена (планшет, 1024 и 768):**
9. Зал без правой колонки бухгалтерии, с единой навигацией и счётчиком.
10. Кухня со стоп-листом в один тап.

**Гость (телефон, 412):**
11. Меню с плотной раскладкой (§7.1–7.5), сжимающаяся шапка, «герой» заведения.
12. Экран «Стол» без пустоты, микро-анимация добавления.
