# Эквайринг для EasyPay: тестовые среды, СБП, чаевые, 54-ФЗ, iiko

Дата исследования: 27.09.2026. Источники — официальные доки провайдеров (ссылки ниже), тарифы
в РФ после 01.01.2026 меняются часто (НДС 22% на эквайринг), поэтому цифры комиссий — ориентир,
а не оферта. Помечено **[?]** — где официального подтверждения не нашёл.

## Главный вывод в одну строку

Настоящая **эмуляция СБП** (QR → статусы «оплачен / отклонён / истёк») есть у **Т-Кассы**
(DEMO-терминал + метод `SbpPayTest`) и у **Яндекс Пэй** (sandbox с эмулятором по сумме).
У **ЮKassa** тестовый магазин получить проще всех (сразу, без юрлица и договора), но СБП в нём
**не тестируется** — только карты и кошелёк ЮMoney.

### iiko / r_keeper

Провайдер эквайринга сам по себе iiko не нужен: EasyPay принимает деньги у своего эквайера и
пишет оплату в iiko **внешним типом оплаты** (`isProcessedExternally: true`), закрывая заказ стола
через iikoCloud API (методы изменения оплат table-заказа и закрытия заказа);
iikoFront API тоже умеет оплатные действия — https://iiko.github.io/front.api.doc/v6/ru/Payments.html.
Открытый вопрос на юриста/бухгалтера: **кто пробивает чек** — облачная касса эквайера («расчёт в
интернете») или ККТ ресторана через iiko. Двойной фискализации быть не должно.

## Рекомендация

### С чего начать тест сегодня

1. **ЮKassa — прямо сегодня, без юрлица.** Регистрация → тестовый магазин → `shopId` + тестовый
   ключ. Гоняем весь контур: создание платежа с `Idempotence-Key` = наш `idemKey`, редирект/виджет,
   вебхук `payment.succeeded` → сервер дописывает платёж в стол → SSE-снапшот, частичный возврат.
   Приятная мелочь: ЮKassa шлёт уведомления только на 443/8443, а наш стенд как раз на
   `https://77-221-141-238.sslip.io:8443`. Ограничение: СБП тут не проверить.
2. **Т-Касса DEMO — как только есть ИП/ООО (или ресторан-пилот).** Единственный из крупных, где
   СБП эмулируется честно: `Init` → `GetQr` → `SbpPayTest` с успехом / отказом / истечением —
   ровно те ветки, которых у нас нет («ошибка платежа», «гость ушёл с QR»). Если юрлица пока нет —
   параллельно **Яндекс Пэй sandbox** как второй способ проверить СБП-статусы (тоже нужен ИП/ООО).

Под это в коде: интерфейс `PaymentProvider` (create/status/refund/webhook-verify) за `pay`, чтобы
ЮKassa-тест и Т-Касса-прод были двумя адаптерами. Сумму по-прежнему считает только сервер.

### Что выбрать для прода (один ресторан)

- **Основной: Т-Касса (или эквайер, который уже обслуживает ресторан-пилот).** СБП 0,4–0,7% без
  НДС, T-Pay/SberPay/карты в одной форме, 14 облачных касс включая свою «Чеки Т-Бизнес»
  и CloudKassir, сплит `Shops[]` на будущее, и чаевые через CloudTips той же группы.
  Минус — нет заголовка идемпотентности: дедуп по `OrderId` на нашей стороне (у нас уже есть `idemKey`).
- **Запасной / быстрый старт: ЮKassa.** Лучший DX и идемпотентность из коробки, но СБП — по
  индивидуальному тарифу, карты 2,8% + НДС; брать, если ресторан не хочет открывать р/с в Т-Банке.
- **Не брать для СБП-сценария:** Robokassa (СБП 1,8–2,7% — дороже эквайринга у банков),
  Альфа/Сбер — только если ресторан уже их клиент (тест выдают после договора).
- **Чаевые:** CloudTips/«Онлайн-чаевые» Т-Бизнеса — ссылка официанта, деньги мимо счёта.
- **Касса:** облачная у эквайера (Чеки Т-Бизнес / CloudKassir / АТОЛ Онлайн) на старте;
  связка с iiko — внешний тип оплаты, решить, чей чек главный.

## Что проверить до выбора (может быть устаревшим)

- Действует ли ещё публичный тестовый терминал `TinkoffBankTest` из старых SDK-примеров — не проверял,
  не полагаться.
- Точная ставка СБП для MCC 5812 (общепит): ЦБ разрешает банкам до 0,7% (0,4% — социально значимые
  категории), потолок 1 500 ₽; у конкретного банка — по заявке.
- Тестируется ли СБП в CloudPayments / Robokassa / PayMaster — в доках не нашёл, спросить поддержку.
- Публичный API CloudTips для автосоздания получателей-официантов.
