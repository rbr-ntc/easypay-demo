# Платежи и фискализация

Статус: скелет. Полные детали — в [../PRD.md](../PRD.md), раздел 8.

## Способы оплаты (MVP)

Приоритет в UI: **СБП** (комиссия 0,4–0,7% против ~2,5% эквайринга) → карта → кошельки.
Один эквайер на старте: Тинькофф или ЮKassa (решается по клиенту).

## Поток платежа (СБП, dine-in)

```
Гость: «Оплатить своё · 1 357 ₽»
  → Backend: рассчитать сумму от НЕОПЛАЧЕННОГО остатка,
    залочить позиции персоны (TTL ~5 мин), создать Payment(idem_key)
  → Шлюз: динамический QR СБП (qrcId, сумма зашита)
  → Гость платит в приложении банка
  → Webhook о зачислении (проверка подписи; всегда отвечаем 200)
  → Backend: Payment=paid, разлочить, PosAdapter.registerExternalPayment(...)
  → Касса бьёт фискальный чек → ОФД → ФНС
  → Уведомление официанту; обновление экранов стола (live)
```

Ошибки: неуспех/таймаут → разлочить позиции, Payment=failed, кнопка «Повторить»
(тот же idem_key → не задваивается). Возврат: по динамическому QR (Start Refund, qrcId).

## Правила против двойной оплаты (из разбора прототипа)

1. Все суммы опций («своё / поровну / весь стол») считаются от неоплаченного остатка.
2. На время активной транзакции одного гостя его позиции залочены для других.
3. «Оплатить весь стол» при частичной оплате = остаток стола, не полная сумма.

## Фискализация (54-ФЗ)

Модель MVP: **фискализирует касса ресторана** (iiko/R-keeper → существующий ОФД).
- Платёж в приложении = «внешний» для кассы (`isProcessedExternally=true`).
- Если когда-нибудь чек бьёт провайдер (Тинькофф Чеки) — ставим `isFiscalizedExternally=true`
  и касса НЕ бьёт второй чек. **Одна сумма — ровно один чек.**
- С 01.03.2025: оплата «у стола» — чек ДО оплаты (делает касса, на UX не влияет);
  полностью дистанционная оплата — «оплата → чек».
- Кто бьёт чек — зафиксировать в договоре с эквайером (главный регуляторный риск).

## Чаевые

**Только напрямую официанту-физлицу** (дарение: без чека, без НДФЛ/взносов у ресторана).
MVP: интеграция нетмонет или CloudTips (бесплатны для заведения, дружат с iiko/R-keeper).
Никогда не проводить чаевые через счёт ресторана.

UI-правило (из разбора прототипа): проценты чаевых считаются от фактически оплаченной
гостем суммы; экран чаевых показывает подтверждение «✓ Оплачено N ₽» сверху.
