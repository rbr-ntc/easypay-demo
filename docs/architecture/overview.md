# Архитектура EasyPay — обзор

Статус: скелет (до старта разработки). Источник требований: [../PRD.md](../PRD.md).
Детали по направлениям: [pos-integrations.md](pos-integrations.md), [payments-fiscal.md](payments-fiscal.md).

## Принципы (зафиксированы)

1. **Касса ресторана (iiko/R-keeper) — единый источник истины** по заказу и счёту.
   EasyPay никогда не «владеет» заказом — только отражает и мутирует через кассовый API.
2. **Идемпотентность всюду**: каждая мутация (позиция, платёж) несёт идемпотентный ключ;
   повтор запроса не создаёт дубль.
3. **Адаптерный слой**: бизнес-логика не знает, какая касса стоит. Один интерфейс
   `PosAdapter`, две реализации (iiko REST / RK7 XML).
4. **Одна сумма — один фискальный чек** (защита от двойной фискализации, см. payments-fiscal).
5. **Деградация**: касса недоступна → режим «только просмотр» (меню видно, заказ/оплата
   заблокированы с честным сообщением).

## Компоненты

```
                       ┌─────────────────┐
  QR на столе ────────▶│ Guest Web-App    │  PWA, без установки (MVP-канал)
                       │ (React/Next PWA) │
                       └────────┬────────┘
                                │ HTTPS/WebSocket (live-обновления стола)
                       ┌────────▼────────┐
                       │   Backend API    │  сессии стола, персоны, корзины,
                       │  (бизнес-логика) │  волны отправки, расчёт долей
                       └──┬─────┬─────┬──┘
              ┌───────────┘     │     └───────────┐
     ┌────────▼───────┐ ┌──────▼──────┐ ┌────────▼────────┐
     │ POS Integration │ │  Payments   │ │  Notifications  │
     │  PosAdapter:    │ │  Adapter:   │ │  push/Telegram  │
     │  - IikoAdapter  │ │  СБП, карта │ │  официант/админ │
     │  - RKeeperAdapter│ │  (Тинькофф/ │ └─────────────────┘
     └────────┬───────┘ │   ЮKassa)   │
              │         └──────┬──────┘
     ┌────────▼───────┐ ┌──────▼──────┐
     │  iiko Cloud /   │ │ Шлюз банка  │──▶ фискализация: касса
     │  RK7 XML (касса)│ │  + webhooks │    ресторана → ОФД → ФНС
     └────────────────┘ └─────────────┘
```

- **Guest Web-App (PWA)** — единственный клиент MVP. Планшет официанта — фаза 2.
- **Backend** — держит то, чего нет в кассе: персоны, привязку позиций к персонам,
  доли общих блюд, волны отправки, статусы оплат по персонам.
- **DB (PostgreSQL)** — сущности + маппинги на ID кассы + идемпотентные ключи + журнал событий.
- **Message bus / очередь** — гарантированная доставка событий (webhook платежа → отметка
  в кассе → уведомление официанту), retry с backoff.

## Ключевые сущности (черновик)

| Сущность | Главные поля | Маппинг на кассу |
|---|---|---|
| TableSession | стол, ресторан, статус, created_at | iiko orderId / RK7 visit+ident |
| Persona | имя, аватар-зверь, session_id | iiko guest / RK7 GuestLabel (seat) |
| CartItem | блюдо, модификаторы, persona_id или shared, волна | iiko item / RK7 Dish (seat/line_guid) |
| SharedSplit | item_id, режим (поровну/доли/назначено), участники | вычисляется у нас |
| Wave | набор CartItem, отправлено на кухню at | iiko add_items / RK7 SaveOrder |
| Payment | persona_id, scope (своё/поровну/стол), сумма, статус, idem_key | внешний платёж кассы |

## Сквозные потоки (dine-in, MVP)

1. **Открытие**: скан QR → session по столу → PosAdapter.getOrCreateOrder(стол).
2. **Заказ**: добавление блюда → CartItem(persona) → при отправке волны →
   PosAdapter.addItems(волна) → касса печатает на кухню → webhook подтверждения.
3. **Оплата**: гость выбирает scope → расчёт суммы от **неоплаченного остатка** →
   платёжная сессия (лок на позиции!) → шлюз → webhook успеха →
   PosAdapter.registerExternalPayment(isProcessedExternally) → чек бьёт касса.
4. **Закрытие**: остаток 0 → PosAdapter.closeOrder; остаток >0 и гости ушли →
   остаток виден официанту, дозакрытие на кассе.
