# Переход из демо в продукт

Демо доказало продуктовую гипотезу и вычистило логику: деньги, роли, кухня и зал работают,
правила зафиксированы тестами. Дальше упираемся не в фичи, а в фундамент — состояние живёт
в памяти одного процесса. Этот документ описывает, что нужно сделать, чтобы получился
продукт, который можно поставить в реальный ресторан.

Документ — план и источник решений. Что уже работает в демо, описано в `CLAUDE.md`.

---

## 1. Что меняется в постановке

| | Демо (сейчас) | Продукт |
|---|---|---|
| Состояние | `Map` в памяти, рестарт = чистые столы | Postgres, ничего не теряется |
| Заведение | одно, зашито в `hall.json` | много ресторанов и точек, данные изолированы |
| Меню | файл в репозитории | данные в БД + кабинет + импорт из кассы |
| Персонал | `staff.json` с PIN в открытом виде | сотрудники в БД, хеши PIN, кабинет, увольнение |
| Деньги | `pay` просто дописывает платёж | эквайринг, фискализация, возвраты, сверка |
| Журнал | 400 записей в памяти | неизменяемый журнал в БД с фильтрами и экспортом |
| Отчётность | сводка смены на лету | реестр чеков, отчёты по официантам, блюдам, сменам |
| Масштаб | один процесс | несколько инстансов за балансировщиком |

Главный вывод по итогам тестовых смен: **всё, что агенты не смогли закрыть в демо
(реестр чеков, персистентный журнал, гашение сессий, food cost), упирается ровно в этот
переход.** Городить их поверх памяти — значит писать половину БД руками.

---

## 2. Целевая архитектура

Монорепозиторий, три слоя с жёсткими границами:

```
apps/
  api/          — HTTP + SSE, авторизация, транзакции, интеграции
  web-guest/    — гостевое web-app по QR (то, что сейчас src/screens)
  web-staff/    — зал, кухня, стол, кабинет (сейчас src/hall, src/kitchen, src/waiter)
packages/
  domain/       — правила без ввода-вывода: деньги, статусы зала, очередь кухни,
                  роли, аллергены. Сюда переезжает нынешний shared/ целиком
  contracts/    — типы API и события, общие для сервера и клиентов
  db/           — схема, миграции, репозитории
  pos/          — PosAdapter: iiko, R-keeper, заглушка
  payments/     — провайдер эквайринга, СБП, фискализация
infra/
  docker-compose.yml, миграции, сиды, наблюдаемость
```

Правило границ: `domain` не знает про HTTP и БД, `api` не считает деньги сам, клиенты не
считают ничего, что влияет на списание. Это уже соблюдается в демо (`shared/money.js`,
`shared/hall.js`, `shared/kitchen.js`, `shared/roles.js`, `shared/allergens.js`) — при
переезде эти файлы становятся ядром `packages/domain` почти без правок вместе с тестами.

**Стек**: Node 22 + TypeScript, Fastify (HTTP + SSE), Postgres 16, Drizzle ORM + drizzle-kit
(миграции как код), Redis (pub/sub для SSE между инстансами, лимиты, блокировки),
BullMQ (фискализация, вебхуки, отчёты), Docker Compose локально.

Почему так: Fastify и Drizzle — минимальная магия и явный SQL, что важно для денег;
Postgres — транзакции и `SELECT … FOR UPDATE` для операций со счётом; Redis нужен не как
кэш, а как шина событий, иначе SSE перестанет работать при втором инстансе.

## 3. Данные

Ключевые сущности (все с `restaurant_id`, мягкое удаление там, где нужна история):

```
restaurants        id, name, timezone, settings
venues             id, restaurant_id, name              — точка/филиал
zones              id, venue_id, name, sort
tables             id, venue_id, zone_id, number, seats, qr_slug
staff              id, restaurant_id, name, role, pin_hash, active_from, active_to
staff_sessions     id, staff_id, device_label, issued_at, expires_at, revoked_at
shifts             id, venue_id, opened_by, opened_at, closed_at, cash_report
table_sessions     id, table_id, shift_id, opened_at, closed_at, closed_by, closed_with_debt
guests             id, table_session_id, name, animal, secret_hash, joined_at
order_lines        id, table_session_id, guest_id, dish_id, name, price, qty, options,
                   shared_with[], sent_at, started_at, started_by, served_at, served_by,
                   cancelled_at, cancelled_by, cancel_reason
payments           id, table_session_id, guest_id, amount, method, provider_id, status,
                   fiscal_receipt_id, created_at
refunds            id, payment_id, amount, reason, status, fiscal_receipt_id
tips               id, table_session_id, guest_id, waiter_id, amount, payout_status
calls              id, table_session_id, guest_id, reason, created_at, ack_at, ack_by
menu_categories    id, restaurant_id, name, sort, schedule
menu_dishes        id, restaurant_id, category_id, name, desc, price, photo_url,
                   allergens[], diet_tags[], station, stop_until, sort, pos_external_id
menu_options       id, dish_id, name, choices(jsonb с adds/removes по аллергенам)
audit_log          id, restaurant_id, at, actor_type, actor_id, session_id, device,
                   action, table_id, entity, amount, payload(jsonb)
```

Инварианты, которые обязаны жить в БД, а не в коде:

- сумма позиции фиксируется в `order_lines.price` при заказе (уже так в демо);
- `shared_with` — список гостей на момент отправки на кухню (уже так в демо);
- платёж не может превышать неоплаченный остаток — проверка в транзакции с блокировкой
  строки сессии стола;
- закрытие сессии с долгом или переплатой создаёт запись в `audit_log` и в отчёте смены;
- отмена позиции хранит `cancelled_by`, причину и была ли позиция в работе — это основа
  списаний (food cost), которых сейчас нет нигде.

## 4. Что переносим как есть

Переезжает без переписывания (вместе с тестами — их уже 76):

- `shared/money.js` — счёт = отправленное, доля общего фиксируется, цена в позиции;
- `shared/hall.js` — статусы столов и пороги внимания;
- `shared/kitchen.js` — очередь, срочность, сводка;
- `shared/roles.js` — матрица прав;
- `shared/allergens.js` — справочник и расчёт с учётом модификаторов;
- гостевой поток и экраны персонала целиком (UI переиспользуется).

Переписывается:

- `server/index.mjs` — состояние в памяти, ручной роутер, журнал массивом;
- `staff.mjs` — сессии в `Map`, PIN в файле;
- `hallplan.mjs`, `menu.mjs` — чтение JSON с диска.

## 5. Личности и доступы

Три разных типа входа, сейчас смешанные:

**Гость** — как в демо: личный секрет из `join`, живёт в браузере, привязан к сессии стола.
В БД хранить хеш секрета, не сам секрет. Логина нет и не нужно.

**Станция смены** (зал, кухня, стол) — вход по PIN, как сейчас. Что добавить:
- PIN хранится хешем (bcrypt/argon2), в файле его быть не должно;
- сессия привязана к устройству (`device_label`), видна менеджеру списком;
- **новый вход не должен оставлять старые токены живыми** — по итогам смены агентов
  под одним PIN работали две сессии одновременно, и журнал их не различал;
- увольнение = `active_to` + отзыв всех сессий сотрудника одним действием;
- каждое действие в журнале несёт `staff_id` **и** `session_id`.

**Кабинет** (владелец, управляющий, бухгалтер) — отдельный контур: email + пароль + 2FA,
не PIN. PIN — это для планшета на кухне, где его вводят сорок раз за смену; кабинет
управляет деньгами и людьми, ему нужна нормальная аутентификация и журнал входов.

## 6. Кабинет

Разделы, каждый закрывает конкретную дыру, найденную в тестовых сменах:

1. **Смены** — открытие/закрытие, X- и Z-отчёты, реестр чеков: по каждой закрытой сессии
   стола позиции с ценами, платежи, чаевые, долг, переплаты, официант. Это то, чем сводят
   кассу; сейчас выручку невозможно сверить с первичкой.
2. **Меню** — категории, блюда, цены, фото, модификаторы с влиянием на аллергены,
   стоп-лист в один тумблер (мгновенно у всех гостей), расписание (завтрак/обед/бар).
   Обязательное поле аллергенов с явным «пусто».
3. **Зал** — план, зоны, столы, посадка, генерация и печать QR, закрепление официантов.
4. **Персонал** — сотрудники, роли, PIN, активные сессии и кнопка «завершить все»,
   график смен.
5. **Аналитика** — выручка по часам и дням, оборачиваемость стола, средний чек на гостя,
   скорость кухни по цехам, топ и аутсайдеры меню, списания (food cost), конверсия чаевых,
   отчёт по официантам.
6. **Журнал** — неизменяемый, с фильтрами по столу, сотруднику, периоду, суммам и экспортом.
7. **Настройки** — реквизиты, эквайринг, касса, фискализация, пороги алертов зала и кухни
   (сейчас зашиты в код), тексты и языки.

Вход в кабинет — отдельный домен/маршрут (`/admin`), не тот же экран, что у смены.

---

## 7. Деньги, фискализация, реестр

- Платёж проходит через провайдера (СБП приоритетно), у платежа есть статус и id провайдера;
  подтверждение приходит вебхуком, а не «нажали кнопку». Появляется состояние «ошибка
  платежа», которого в демо нет.
- Возвраты — сущность первого класса: переплата при отмене неподанного (уже фиксируется
  в демо строкой журнала) должна становиться `refunds` с фискальным чеком.
- 54-ФЗ: чек на каждый платёж и возврат, ссылка на чек гостю, реквизиты в настройках.
- Чаевые остаются вне выручки ресторана и выплачиваются официанту — нужен реестр выплат.
- Сверка: отчёт «выручка = закрытые сессии + оплаченное на открытых», расхождение подсвечивать.

## 8. Касса

`packages/pos` с интерфейсом `PosAdapter` из `docs/architecture/pos-integrations.md`:
`iiko`, `rkeeper`, `none`. Развилка, которую надо принять до кабинета меню: **в проде
источник цен и состава — касса**, а кабинет владеет тем, чего в кассе нет (фото, описания,
аллергены, модификаторы для гостя, стоп-лист, расписание). Синхронизация по
`pos_external_id`, конфликт разрешается в пользу кассы по цене и в пользу кабинета
по витрине.

---

## 9. Реалтайм на нескольких инстансах

Сейчас SSE рассылается из памяти процесса. В проде: мутация → запись в БД → событие в Redis
pub/sub → каждый инстанс рассылает своим подписчикам. Формат событий остаётся прежним
(полный снапшот стола, компактные карточки зала, тикеты кухни) — клиенты не переписываются.
Токен для SSE перенести из query в cookie сессии.

---

## 10. Наблюдаемость

- Журнал действий — в БД, append-only, с `session_id` и устройством.
- Метрики: время до первого заказа, время кухни по цехам, время до оплаты, доля столов,
  закрытых с долгом, доля отменённых позиций.
- Алерты: расхождение сверки, всплеск отмен, зависшая очередь кухни, ошибки эквайринга.
- Ошибки — Sentry или аналог; сейчас всё живёт в `console.error`.

## 11. Этапы

**Этап 1. Фундамент (2–3 недели).** Монорепо, Postgres, схема и миграции, перенос
`shared/` в `packages/domain`, `apps/api` на Fastify с теми же эндпоинтами, состояние из
БД, Redis для SSE. Критерий готовности: текущие 76 тестов зелёные на новой основе, демо
работает как раньше, рестарт больше ничего не теряет.

**Этап 2. Смена и деньги (2 недели).** Сотрудники и сессии в БД, хеши PIN, отзыв сессий,
реестр чеков, журнал с фильтрами, возвраты и переплаты, отчёт смены. Критерий: касса
сводится за смену без ручного пересчёта.

**Этап 3. Кабинет (3 недели).** Меню с расписанием и стоп-листом, зал и QR, персонал,
аналитика, настройки. Критерий: новое заведение заводится без разработчика.

**Этап 4. Внешний мир (по договорённостям).** Эквайринг и фискализация, `PosAdapter`
под кассу первого клиента, домен и HTTPS, пилот на одном ресторане.

## 12. Решения, которые нужно принять сейчас

1. **Один ресторан или SaaS с самого начала.** Схема с `restaurant_id` дешевле сразу,
   чем ретрофитом.
2. **Касса первого клиента** — iiko или R-keeper: от этого зависит адаптер и то, кто
   владеет ценами.
3. **Эквайер и оператор фискализации** — от этого зависят возвраты и чеки.
4. **Хостинг**: остаёмся на своей VPS (нужен домен, HTTPS, бэкапы Postgres) или уходим
   в управляемую БД у провайдера.
5. **Где живёт кабинет** — тот же домен с `/admin` или отдельный поддомен.

До этих ответов Этап 1 можно делать целиком: он не зависит ни от кассы, ни от эквайера.
